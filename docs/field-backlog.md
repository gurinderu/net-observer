# Полевой бэклог — вимарши к заведению в граф

> Это НЕ источник истины и не роадмап. Это очередь вопрошаний, собранная из
> полевого дежурства за маком (сентябрь 2026): инструменты, которые пришлось
> поднимать вручную по SSH + shell, потому что net-observer их пока не умеет.
> Каждый пункт — кандидат в `vimarsha` реалма `net-observer`; залить в граф
> скиллом с `nks_*` (эта сессия их не имела). Правило, которое всё это родило:
> диагностика и доказательная база должны выходить ИЗ продукта, а не из
> ad-hoc грепов чужого лога.

---

## V-A · Живая форензика через сокет

**Наблюдение.** `why`, `incident-context`, `gateway-ramp`, `query` — offline-only:
DuckDB держит эксклюзивный замок, пока демон жив, так что команды требуют
остановить демон и root. Ровно в момент инцидента (когда форензика и нужна)
живой сокет отдаёт только `status` + список инцидентов без деталей. Из-за
этого весь разбор бан-цикла 16.09 шёл через `ssh + grep` лога shell-оракула,
а не через net-observer-cli.

**Answered when.** Есть read-only путь к форензике при живом демоне —
WAL-read / snapshot-запрос / read-реплика — и `why`/`incident-context`/
`gateway-ramp` отвечают по сокету без остановки демона.

## V-B · BSSID / SSID / per-iface MAC в link-коллекторе + сигнатура roam

**Наблюдение.** Причина «бан-карусели» на коворкинге 16.09 оказалась в
роуминге macOS между задвоенными SSID (5G/6G) одной точки с пер-SSID
Private Wi-Fi MAC: каждый роам = новый MAC = DHCP-identity с нуля. Поймать
это удалось только ручным опросом `ipconfig getsummary en0` (BSSID/SSID) и
`ifconfig en0 ether` (MAC) — link-коллектор не пишет ни BSSID, ни SSID, ни
MAC интерфейса, поэтому класс маскировался под `gw-drop` / `per-client-block`.

**Answered when.** link-коллектор снимает BSSID, SSID и MAC интерфейса
каждый тик; есть сигнатура `roam`/`reassoc`, срабатывающая на смену BSSID
или MAC, с явным следствием «DHCP-identity сменилась» — так SSID-роам и
band-steering становятся первоклассным инцидентом, а не шумом в других.

## V-C · Бан-цикл как единый эпизод

**Наблюдение.** Паттерн «2–4 минуты жизни → блок → разбан, по кругу» сейчас
пишется россыпью независимых `gw-drop`/`gw-change`/`per-client-block` —
за день их накапливаются десятки, и «тебя циклит» не читается как один факт
с периодом. Оператору (и тем более для доказательства третьей стороне)
нужен именно цикл, а не 40 разрозненных строк.

**Answered when.** Есть сигнатура более высокого порядка, распознающая
N ban/unban-переходов в окне как ОДИН эпизод с измеренным периодом и числом
итераций.

## V-D · Режим контролируемого эксперимента (бисекция) через CLI

**Наблюдение.** Чтобы ответить «это мы или сеть», 16.09 пришлось вручную
гонять фазы A/B/C/D: `observe off`, `SetQuiet`, `launchctl bootout sing-box`,
и мерить ритм банов внешним пингом. Всё это — ssh-пляска поверх продукта.

**Answered when.** Есть CLI-режим эксперимента: пауза выбранных КЛАССОВ
собственных эмиссий демона, запись маркера границы фазы в БД, и отчёт
«incident-rate по фазам». «Это мы или сеть» становится командой продукта,
а не ручной процедурой. (Осторожно с выводами: фаза должна длиться ≥3–4
периодов исходного ритма — короткое чистое окно неотличимо от везения; урок
16.09, когда 6-минутная фаза дала ложный вердикт.)

## V-E · Per-flow-kill (дыра established-stall)

**Наблюдение.** Отдельный класс, который не увидела ни одна сигнатура:
dial sing-box к КОНКРЕТНОМУ endpoint'у таймаутится, пока сырая TCP-проба к
тому же endpoint зелёная за ~44 мс. Улика живёт только в ERROR-логе самого
sing-box («dial tcp … i/o timeout» при OK в vless[]-колонке). Middlebox
душит именно established-потоки прокси к выбранному серверу.

**Answered when.** Есть сигнатура, кросс-проверяющая dial-фейлы (из Clash
API / лога) против зелёной сырой пробы того же endpoint'а в тот же тик —
родня middlebox-детектору «connect быстрее физического RTT».

## V-F · Внешняя достижимость как ось инцидента *(ниже приоритетом)*

**Наблюдение.** Понимание «был ли бокс вообще достижим снаружи» жило целиком
в моём shell-мониторе (tailnet-пинг + логика «слепого окна»). Для демона это
внешняя перспектива и потому вторично, но у инцидента есть неснятая ось:
достижимость с чужой точки во время эпизода.

**Answered when.** Решено явно — либо ось «reachable-from-outside» у
инцидента заведена, либо сознательно оставлена вне контура демона с пометкой
«это внешний наблюдатель, не его забота».
